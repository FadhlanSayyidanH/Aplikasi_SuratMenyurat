# Lampiran & OnlyOffice

Letter attachments (photos, PDF, DOCX/PPTX/XLSX) with in-browser preview/edit/annotation via OnlyOffice Document Server, plus an opt-in encryption-at-rest option.

## Key files
- Model: `app/Models/SuratFile.php`, `app/Models/SuratFileAnnotation.php`
- Service: `app/Services/SuratFileService.php` (upload/compress/store), `app/Services/FileEncryptionService.php` (AES-256-CBC via `APP_KEY`), `app/Services/OnlyOfficeJwtService.php` (signs editor config JWT)
- Web: `app/Livewire/SuratFileEditor.php` (`/lampiran/{suratFile}/editor` — DOCX/PPTX/XLSX/PDF via OnlyOffice), `app/Livewire/SuratFileAnnotate.php` (`/lampiran/{suratFile}/coret` — photo markup, opened instead of OnlyOffice when the attachment is an image)
- API: `app/Http/Controllers/Api/OnlyOfficeController.php` (`editDocx`/`editPdf`/`callback` — see `routes/api_files.php`), `app/Http/Controllers/Api/FileServeController.php` (raw file serving via `file_token`, not session auth), `app/Http/Controllers/Api/SuratFileController.php` (add/delete/rename/annotation CRUD)

## Encryption at rest
`FileEncryptionService::encryptedPut()`/`decryptedGet()` — **opt-in for new uploads only**; old files stay plaintext forever, mixed in the same `storage/app/uploads` dir. `decryptedGet()` treats ANY `DecryptException` as "this must be plaintext" and silently returns the raw (possibly still-ciphertext) bytes — **this makes key-mismatch corruption completely silent**, no exception, no log entry, just garbled bytes served to whatever requested the file. `php artisan file:cek-enkripsi` cannot distinguish genuine old plaintext from broken-ciphertext-under-wrong-key either, since it uses the same decrypt-or-assume-plaintext logic.

**Incident (2026-08-29, VPS2 migration)**: 68 of 225 files became unreadable after migrating to a VPS with a freshly-generated `APP_KEY` (files encrypted under the old key can't decrypt under a new one). Detected via a custom scan comparing magic bytes (`%PDF`, `PK` for docx/xlsx/pptx, JPEG/PNG headers) against the claimed extension — NOT via `file:cek-enkripsi`. **If this class of bug is ever suspected again** (e.g. after any future `APP_KEY` rotation or VPS migration), re-run a magic-bytes-vs-decrypt scan before trusting migration checksums — checksums only prove bytes moved correctly, not that they're still decryptable under whatever key the new environment has.

## OnlyOffice integration
- `OnlyOfficeController::editDocx`/`editPdf` (auth.token) return a JWT-signed editor config the client renders via `DocsAPI.DocEditor`; `callback` (no `auth.token` — authenticated via docserver JWT + `file_token` internally) is called BY the Document Server itself on save.
- File-fetch path: Document Server (inside Docker) fetches the file content from Laravel via `ONLYOFFICE_HOST_GATEWAY` (`host.docker.internal:<port>`). On Linux Docker this hostname does **not** resolve unless the container was started with `--add-host=host.docker.internal:host-gateway` — missing this makes the editor shell load fine (JWT/UI auth succeeds) while the actual document fetch silently fails ("File tidak bisa diakses sekarang"), which looks like "almost working." Always include this flag when creating the `onlyoffice-documentserver` container.
- `callback()` (`app/Http/Controllers/Api/OnlyOfficeController.php:230`) is written to fail-safe for most error modes, but `debugLog()` (`:369`) calls `file_put_contents()` on `storage/app/onlyoffice_callback.log` **before** any of that fail-safe logic runs. If that log file loses write access (e.g. after a broad `chown -R` on the app root), Laravel turns the resulting PHP warning into a real `ErrorException`, 500ing the ENTIRE callback endpoint — symptom: document displays fine but shows "Dokumen tidak bisa disimpan" on every edit/close. Fix: `chown www-data:www-data storage/app/onlyoffice_callback.log`.
- File uploads (any `wire:model` file input app-wide, not just OnlyOffice) depend on `storage/app/private` being group-writable by `www-data` (Livewire's upload staging dir lives there). A broad `chown -R` can silently strip the group-write bit, breaking every upload with `League\Flysystem\UnableToCreateDirectory` — quick check: `sudo -n -u www-data test -w storage/app/private`.
- **General lesson**: any broad `chown -R` on this app's tree should be followed by an audit of pre-existing FILES (not just directories) under `storage/`: `sudo find storage bootstrap/cache ! -user www-data -exec ls -la {} \;` — setgid directories self-heal for new files, but existing files keep whatever mode bits they had.
